# C++/Qt から Rust への段階移行計画

Status: Draft

## 1. 目的

tfx for Linux の Qt ベースのユーザーインターフェースと機種依存処理を
維持しながら、内部処理を段階的に Rust へ移行する。

主な目的は次の2点とする。

- メモリ安全性を高め、外部入力やファイル操作に起因する脆弱性のリスクを
  下げる。
- OS 固有処理を明確な境界へ隔離し、Linux 以外へ移植しやすい構成にする。

Rust のコード比率そのものは成果指標としない。危険度の高い処理が安全な
境界内に収まり、OS 依存がコアロジックから除去されたことを重視する。

## 2. 前提と対象外

- Qt Widgets、`QObject`、signal/slot、Qt イベントループは C++ に残す。
- Qt のモデル、ビュー、ウィンドウ、ダイアログは初期移行の対象外とする。
- DBus、デスクトップ連携、ゴミ箱、関連付け、QTermWidget など、Qt または
  OS と密接に結び付く処理はプラットフォーム層に残す。
- 最初に Linux 版の動作互換を維持し、その後に Windows と macOS の
  プラットフォーム実装を検討する。
- 全面書き換えは行わず、機能単位で C++ 実装から Rust 実装へ移行する。

Rust を採用しても、パストラバーサル、権限判定、TOCTOU、リソース枯渇などの
論理的な脆弱性が自動的に解消されるわけではない。入力制限、パス検証、
失敗時の復旧方法を別途仕様化する。

## 3. 目標構成

```text
C++ / Qt UI
  MainWindow、FilePane、models、views、QObject、signal/slot
                         |
                  C++ FFI adapter
                         |
                    Rust core
  入力解析、状態管理、検索、ファイル操作、ZIP 検証
                         |
               platform-neutral API
                         |
              platform implementations
       Linux / Windows / macOS 固有処理
```

Qt のイベントループと UI オブジェクトの所有権は C++ 側が持つ。Rust 側は
Qt 型を認識せず、明示的な入力、結果、エラーを持つライブラリとして構成する。

## 4. モジュールの分類

| 分類 | 初期方針 | 主な対象 |
|---|---|---|
| Qt UI | C++ に残す | `MainWindow`、`FilePane`、views、models |
| Qt 非同期制御 | C++ の薄いラッパーを残す | `FileOperationWorker`、controllers |
| 純粋ロジック | Rust へ移行 | `SearchState`、`TypeAhead`、`TabState` |
| 入力解析 | 優先して Rust へ移行 | `DelimitedText`、Git porcelain 解析 |
| ファイル処理 | 安全要件を定義して Rust へ移行 | `FileOperations`、コピー、移動 |
| プレビュー読み込み | 上限と文字コード仕様を維持して移行 | `PreviewText` |
| OS・Qt 統合 | 当面 C++ に残す | `PlatformLinux`、DBus、ゴミ箱 |
| 外部ツール | 使用継続を個別判断 | `git`、`unzip`、`pdftoppm` |

## 5. 段階計画

### Phase 0: ベースライン調査

目安: 1週間

- Qt、POSIX、Linux API、外部コマンドの利用箇所を一覧化する。
- ZIP、ファイル操作、プレビュー、Git、ユーザーコマンドを脅威分析する。
- 非 UTF-8 ファイル名、大容量ファイル、深い階層、シンボリックリンクの
  現行動作を確認する。
- 既存テストと未検証の異常系を対応付ける。
- Windows と macOS で代替実装が必要になる機能を識別する。

完了条件:

- 各モジュールについて Qt 依存度、OS 依存度、セキュリティ影響、FFI の
  複雑さ、テスト状況、移行優先度が記録されている。
- 現行動作を維持すべき項目と、仕様変更が必要な項目が区別されている。

### Phase 1: C++/Rust 境界設計

目安: 1～2週間

- Cargo crate を `staticlib` として構成し、CMake からリンクする方針を
  確定する。
- 文字列、パス、配列、エラー、キャンセル、進捗通知の FFI 表現を定義する。
- Rust の panic と C++ 例外を言語境界から外へ出さない規約を定める。
- メモリを確保した側が解放する所有権規約を定める。
- `unsafe` を FFI 専用モジュールへ限定する。

完了条件:

- Rust の公開 API に `QString`、`QObject`、`QFileInfo` などの Qt 型が
  含まれていない。
- UI スレッド、ワーカースレッド、コールバック寿命の責任範囲が明確である。
- Linux の非 UTF-8 パスと Windows のネイティブパスを失わない設計である。

### Phase 2: ビルド統合 PoC

目安: 1～2週間

最初の対象は `TypeAhead` または Git porcelain の解析処理とする。PoC では
セキュリティ効果よりも、次の技術成立性を確認する。

- CMake から Cargo のビルドを実行できる。
- Rust 静的ライブラリをアプリとテストへリンクできる。
- C++ と Rust のテストを同じ CI で実行できる。
- Release、Debug、sanitizer ビルドの運用が成立する。
- Rust 実装を無効化して C++ 実装へ戻せる。

PoC 用ブランチは実装ブランチと分離し、そのまま製品コードへマージすることを
前提としない。成立した設計だけを小さな変更として再実装する。

### Phase 3: セキュリティ重点移行

目安: 4～6週間

次の順で移行する。

1. ZIP エントリー名、展開先、シンボリックリンクの検証
2. ZIP の展開サイズ、ファイル数、階層深度の制限
3. ファイルのコピー、移動、再帰、上書き、キャンセル
4. 外部コマンドの引数、実行ファイル、タイムアウトの管理
5. テキスト、CSV/TSV、Git 出力など外部入力の解析

`FileOperationWorker` は `QObject` として C++ に残し、Rust 処理の開始、
キャンセル、進捗、完了を仲介する。

完了条件:

- `../`、絶対パス、Windows 形式パスを含む ZIP が展開先から脱出しない。
- シンボリックリンクを経由したコピー・展開先脱出を防止できる。
- ファイル数、展開サイズ、階層深度、読み込みサイズに上限がある。
- コピーや上書きの失敗時に既存データが保持される。
- キャンセル後に一時ファイルや半端な出力が残らない。

### Phase 4: コアロジック移行

目安: 2～4週間

候補順:

1. `SearchState`
2. `TypeAhead`
3. `DelimitedText`
4. `TabState`
5. `SidebarLogic`
6. `GitService` の解析処理
7. `PreviewText`
8. パス正規化、重複名生成、移動先検証

Qt 側の公開クラスは維持し、内部実装のみを Rust 呼び出しへ置き換える。
各機能は独立した変更としてレビューし、既存 C++ 版と同じテストケースを
Rust 単体テストでも実行する。

### Phase 5: プラットフォーム境界の整理

目安: 2～4週間

- OS 機能を明示的な Platform API に集約する。
- コアロジックから DBus、`xdg-*`、`/proc`、POSIX 固有 API を除去する。
- 外部コマンドの存在と機能を実行時に判定する。
- Linux 以外の実装で必要になる機能差を API 上で表現する。

端末埋め込み、DBus、ファイル関連付け、ゴミ箱、PDF 変換は、移植上の利点が
確認できるまで C++ のプラットフォーム実装に残してよい。

### Phase 6: 品質保証と配布

目安: 2～3週間

- Rust 単体テストと Qt 結合テストを CI で実行する。
- 残る C++ を ASan、UBSan、コンパイラ警告で検査する。
- `cargo audit` と `cargo deny` で依存関係を監査する。
- ZIP、パス、入力解析へファズテストとプロパティテストを追加する。
- Debug、Release、パッケージビルドを検証する。
- Rust ランタイムと依存ライブラリを含む配布物のライセンスを確認する。

### Phase 7: 他 OS への展開

Linux 版で境界が安定した後、Windows と macOS の Platform 実装を追加する。
OS ごとにファイル名、権限、リンク、ゴミ箱、関連付け、端末の差をテストする。

## 6. セキュリティ要件

- 信頼できないファイル内容とファイル名を常に外部入力として扱う。
- パス検証では文字列の前方一致ではなく、OS のパス表現とファイルシステムの
  性質を考慮する。
- チェック後に対象が差し替わる TOCTOU を可能な範囲で避ける。
- 上書きは同一ファイルシステム上の一時ファイルと atomic rename を基本とする。
- 外部コマンドはシェル文字列ではなく、実行ファイルと引数列で起動する。
- 処理時間、メモリ、入力サイズ、出力サイズ、ファイル数に上限を設ける。
- FFI を通過するポインター、長さ、enum 値を Rust 側でも検証する。
- ログへ機密性のあるパスやユーザーデータを不用意に出力しない。

## 7. 移植性要件

- Rust コアは Qt と Linux 固有 API に依存しない。
- パスを通常の UTF-8 文字列として固定しない。
- パス区切り、大小文字、予約名、権限、作成日時の差を仕様に含める。
- OS が機能を提供しない場合をエラーではなく capability として表現する。
- 外部コマンド依存には代替処理または機能無効化の方針を持つ。

## 8. ライセンスと依存関係

本プロジェクトのライセンスは Apache License 2.0 とする。

Rust crate を追加する際は次を確認する。

- Apache-2.0 と両立するライセンスであること。
- コピーレフト条件、NOTICE 条件、ソース提供条件の有無。
- メンテナンス状況、公開済み脆弱性、推移的依存関係。
- Qt、QTermWidget、外部コマンドを含む配布物の第三者ライセンス表記。

`Cargo.lock` をアプリケーションの再現可能なビルド情報として管理し、
依存関係の追加と更新は個別にレビューする。

## 9. ブランチと変更単位

計画文書:

```text
docs/rust-migration-plan
```

技術検証:

```text
spike/rust-ffi-poc
```

実装例:

```text
feature/rust-build-integration
feature/rust-type-ahead
feature/rust-zip-validation
feature/rust-file-operations
feature/platform-abstraction
```

全移行を1本の長期ブランチで進めない。ビルド基盤、各機能、Platform 整理を
別々にレビューし、各段階でリリース可能な状態を維持する。

## 10. 評価指標

- 外部入力を直接処理する C++ コードの削減量
- FFI 境界と `unsafe` コードの規模
- Platform 層外に残る Linux 固有処理の数
- 外部コマンド依存の数
- 異常系、攻撃系、キャンセル、復旧テストの実施状況
- sanitizer、依存監査、ファズテストの結果
- 配布物サイズ、起動時間、ファイル操作性能への影響

Linux 版の Rust コア移行は、1名で12～18人週を初期目安とする。Windows と
macOS の実対応は、OS ごとに追加3～6人週を仮置きする。Phase 0 の調査後に
対象範囲と見積もりを更新する。
